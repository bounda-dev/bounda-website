This tutorial builds a small order API with event sourcing and deploys it to Cloudflare. It
uses [Bounda](https://docs.bounda.dev/getting-started/), an event sourcing and CQRS framework for
TypeScript, and its Cloudflare adapter, which runs each tenant of your app in its own
[Durable Object](https://developers.cloudflare.com/durable-objects/): the event store, the read
models and the background work, all in the object's SQLite. There is no database to provision and
no queue or cron to run.

By the end you will have placed orders, paid them, let an unpaid one expire on a timer, tested all
of it inside workerd and deployed it with one command. It takes about half an hour. You need
Node.js 22.18 or later, and a Cloudflare account for the last step; the free plan is enough.

## 1. Create the project

```bash
npm create bounda@latest my-app -- --runtime cloudflare
cd my-app
```

That writes the project, initialises a git repository and installs the dependencies. If you
would rather start from GitHub, the
[Deploy to Cloudflare](https://deploy.workers.cloudflare.com/?url=https://github.com/bounda-dev/bounda-cloudflare-template)
button forks [bounda-cloudflare-template](https://github.com/bounda-dev/bounda-cloudflare-template),
the same project, into your account and deploys it; clone your fork and carry on from step 2.

## 2. What you got

The app is an `order` aggregate with one command and one event, and an `orders` read model with
one query. In Bounda a file's folder and name are its declaration, so the tree is the app:

```
app/domain/order/order-placed.ts              the event OrderPlaced
app/domain/order/commands/place-order.ts      the command placeOrder
app/read/orders/view.ts                       the read model's table
app/read/orders/projections/order/order-placed.ts
app/read/orders/queries/list-orders.ts        the query listOrders
bounda.config.ts                              storage: cloudflare()
src/worker.ts                                 the Durable Object class and the HTTP API
wrangler.jsonc                                the binding and the SQLite migration
tests/orders.test.ts                          the domain, on an in-memory store
tests/api.test.ts                             the API, against the Durable Object
```

The command decides; it returns events or a typed rejection, and never touches the database:

```ts
// app/domain/order/commands/place-order.ts
import type { Command } from "./+types/place-order";

export const payload = ({ z }: Command.PayloadArgs) =>
  z.object({ orderId: z.uuid(), customerId: z.string().min(1), total: z.number().positive() });

export const rejections = ({ command }: Command.RejectionsArgs) => ({
  AlreadyPlaced: `Order ${command.aggregateId} was already placed`,
});

export const handler = ({ command, state, events, reject }: Command.HandlerArgs) => {
  if (state.status !== undefined) return reject("AlreadyPlaced");
  return [
    events.orderPlaced({ customerId: command.payload.customerId, total: command.payload.total }),
  ];
};
```

The event says what its payload is and how it changes the order's state:

```ts
// app/domain/order/order-placed.ts
import type { Event } from "./+types/order-placed";

export const payload = ({ z }: Event.PayloadArgs) =>
  z.object({ customerId: z.string(), total: z.number().positive() });

export const begin = ({ event }: Event.BeginArgs) => ({
  status: "placed" as const,
  customerId: event.payload.customerId,
  total: event.payload.total,
});
```

The `+types` imports are generated by `bounda generate`, which every script runs first, so the
state, the events and the commands are typed from these files without a line of wiring.

The Cloudflare part is two exports in `src/worker.ts`:

```ts
// src/worker.ts
import { createBoundaObject, createWorker } from "@bounda-dev/cloudflare";
import { registry } from "../.bounda/registry.ts";
import config from "../bounda.config.ts";

export const Store = createBoundaObject({ registry, config });

export default createWorker({
  config,
  tenantOf: (request) => request.headers.get("x-bounda-tenant") ?? "default",
});
```

`Store` is the Durable Object class, bound as `STORE` in `wrangler.jsonc` and created as a SQLite
class by its migration. `createWorker` is a JSON API in front: `POST /commands/<name>` and
`POST /queries/<name>`, routed to the tenant's object by the `x-bounda-tenant` header.

## 3. Run it

```bash
npm test
```

Both test files run inside workerd, the runtime Cloudflare deploys to, through
[Cloudflare's Vitest integration](https://developers.cloudflare.com/workers/testing/vitest-integration/).
`tests/orders.test.ts` runs the domain on an in-memory store, and `tests/api.test.ts` sends
requests to the Worker and reaches a real Durable Object and its SQLite.

Then start it locally:

```bash
npm run dev
```

`http://localhost:8787` serves a small page that places and lists orders. Or from a terminal:

```bash
curl -X POST localhost:8787/commands/placeOrder \
  -H 'content-type: application/json' -H 'x-bounda-tenant: acme' \
  -d '{"orderId":"018f6a5e-4c3c-7c1e-9d4b-0b2c4a1d8e01","customerId":"ada","total":42}'
```

The answer names the event the command stored and its position in the tenant's global stream:

```json
{"scheduled":false,"aggregateType":"order","aggregateId":"018f6a5e-4c3c-7c1e-9d4b-0b2c4a1d8e01","version":1,"eventIds":["01a1b656-1123-748e-932f-2899972e40c3"],"eventTypes":["OrderPlaced"],"position":1}
```

## 4. Add a real step: pay, or expire

An order that nobody pays should not hold stock forever. The rule: an order can be paid while it
is placed, and an order still unpaid 30 minutes after it was placed expires. That is two events,
two commands and one policy.

The events only change the state. Each file next to `order-placed.ts` is an event of the order:

```ts
// app/domain/order/order-paid.ts
import type { Event } from "./+types/order-paid";

export const evolve = ({ event }: Event.EvolveArgs) => ({
  status: "paid" as const,
  paidAt: event.timestamp,
});
```

```ts
// app/domain/order/order-expired.ts
import type { Event } from "./+types/order-expired";

export const evolve = (_: Event.EvolveArgs) => ({ status: "expired" as const });
```

Paying is refused unless the order is placed. The rejection is typed, and it is an answer, not a
fact: nothing is stored when it happens.

```ts
// app/domain/order/commands/pay-order.ts
import type { Command } from "./+types/pay-order";

export const payload = ({ z }: Command.PayloadArgs) => z.object({ orderId: z.uuid() });

export const rejections = ({ command, state }: Command.RejectionsArgs) => ({
  NotPayable: `Order ${command.aggregateId} is ${state.status ?? "unknown"}, not placed`,
});

export const handler = ({ state, events, reject }: Command.HandlerArgs) => {
  if (state.status !== "placed") return reject("NotPayable");
  return [events.orderPaid()];
};
```

Expiring decides against the state at the moment it runs. If the order was paid in the meantime,
it returns no events and nothing happens:

```ts
// app/domain/order/commands/expire-order.ts
import type { Command } from "./+types/expire-order";

export const payload = ({ z }: Command.PayloadArgs) => z.object({ orderId: z.uuid() });

export const handler = ({ state, events }: Command.HandlerArgs) =>
  state.status === "placed" ? [events.orderExpired()] : [];
```

And the policy ties them together. Its file name says what it reacts to, `OrderPlaced`, and it
schedules `expireOrder` for half an hour later:

```ts
// app/domain/order/policies/expire-on-order-placed.ts
import type { Policy } from "./+types/expire-on-order-placed";

export const handler = async ({ event, commands }: Policy.HandlerArgs) => {
  await commands.expireOrder({ orderId: event.aggregateId }, { delay: "30m" });
};
```

`commands` is typed from your command files: a misspelt command or a wrong payload does not
compile.

To see the status in `listOrders`, give the read model a column and project the two new events.
Add `status` to the view:

```ts
// app/read/orders/view.ts
import type { View } from "./+types/view";

export const fields = ({ f }: View.FieldsArgs) => ({
  orderId: f.string().primaryKey(),
  customerId: f.string().index(),
  total: f.number(),
  status: f.string(),
  placedAt: f.date(),
});
```

Set it in the existing projection, by adding `status: "placed",` to the row that
`projections/order/order-placed.ts` upserts, and add one projection per new event:

```ts
// app/read/orders/projections/order/order-paid.ts
import type { Projection } from "./+types/order-paid";

export const project = async ({ event, table }: Projection.Args) => {
  await table.update({ orderId: event.aggregateId }, { status: "paid" });
};
```

```ts
// app/read/orders/projections/order/order-expired.ts
import type { Projection } from "./+types/order-expired";

export const project = async ({ event, table }: Projection.Args) => {
  await table.update({ orderId: event.aggregateId }, { status: "expired" });
};
```

Run `npm run typecheck`. It regenerates the types and checks the whole app, including the
`status` the new projections write.

If you placed orders in step 3, or deployed with the button, those rows come back without a
status. Bounda adds the new column to the table when the object starts, but a row only gets a
value when a projection touches it again. A read model is derived data, so the fix is to project
the whole stream again with the new code: `rebuildReadModel("orders")` on the client that
`connect` gives you does it without taking the read model offline
([rebuilding a read model](https://docs.bounda.dev/guides/deployment/#rebuilding-a-read-model)).
For the local store of `npm run dev`, deleting `.wrangler/state` is enough.

## 5. Test it, without waiting half an hour

`createTestApp` gives you the app on an in-memory store with a clock that only moves when you move
it. A scheduled command becomes due because the clock moved, never because the test waited:

```ts
// tests/expiry.test.ts
import { createTestApp } from "@bounda-dev/core/testing";
import { describe, expect, it } from "vitest";
import { registry } from "../.bounda/registry.ts";

const orderId = "018f6a5e-4c3c-7c1e-9d4b-0b2c4a1d8e01";
const MINUTE = 60_000;

describe("an order nobody pays", () => {
  it("expires 30 minutes after it was placed", async () => {
    const { app, clock } = await createTestApp({ registry });
    await app.commands.placeOrder({ orderId, customerId: "ada", total: 42 });
    await app.runUntilIdle();

    clock.advance(30 * MINUTE);
    await app.runUntilIdle();

    expect(await app.queries.listOrders({ customerId: "ada" })).toMatchObject({
      orders: [{ orderId, status: "expired" }],
    });
    await expect(app.commands.payOrder({ orderId })).rejects.toMatchObject({
      rejected: "NotPayable",
    });
    await app.stop();
  });

  it("stays paid when it was paid in time", async () => {
    const { app, clock } = await createTestApp({ registry });
    await app.commands.placeOrder({ orderId, customerId: "ada", total: 42 });
    await app.commands.payOrder({ orderId });

    clock.advance(30 * MINUTE);
    await app.runUntilIdle();

    expect(await app.queries.listOrders({ customerId: "ada" })).toMatchObject({
      orders: [{ orderId, status: "paid" }],
    });
    await app.stop();
  });
});
```

And one more case in `tests/api.test.ts`, inside its `describe`, through HTTP and the real
Durable Object. It uses the file's own `post` and `listOrders` helpers:

```ts
it("pays an order, and the next query sees it paid", async () => {
  const orderId = crypto.randomUUID();
  await post("/commands/placeOrder", { orderId, customerId: "ada", total: 42 }, "pays");
  expect((await post("/commands/payOrder", { orderId }, "pays")).status).toBe(200);
  expect(await listOrders("pays", "ada")).toMatchObject({ orders: [{ status: "paid" }] });
});
```

`npm test` now runs ten tests. One of the template's fails first, and rightly: the
`toEqual` in `tests/orders.test.ts` lists every field of the row, so add `status: "placed"` to
it. That is the read model telling you its shape changed.

Paying twice over HTTP shows the rejection as the API returns it, a 409 with the reason:

```json
{"error":{"code":"DOMAIN_ERROR","message":"Order 018f6a5e-4c3c-7c1e-9d4b-0b2c4a1d8e01 is paid, not placed","rejected":"NotPayable"}}
```

## 6. Deploy

```bash
npx wrangler login
npm run deploy
```

`deploy` generates the types and runs `wrangler deploy`, which uploads the Worker, creates the
Durable Object class from the migration in `wrangler.jsonc` and prints your
`workers.dev` address. Use it in place of `localhost:8787` in the `curl` above. To see what would
be uploaded without deploying, `npm run check` type-checks the app and runs
`wrangler deploy --dry-run`.

Before real users reach it: the API of `createWorker` has **no authentication**, on purpose. It
is a starting point, and anyone who knows the address can pick any tenant with the header. An app
with users writes its own `fetch`, decides the tenant from the session and calls the object with
`connect(env.STORE.get(env.STORE.idFromName(tenant)))`, which gives the same typed `commands`
and `queries` as the tests. The [Cloudflare guide](https://docs.bounda.dev/adapters/cloudflare/)
shows it.

## How it runs

Just enough to reason about what you deployed:

- **One Durable Object per tenant.** Each tenant gets its own object, with its own SQLite
  holding its events, its read models, its scheduled commands and the inbox of its policies.
  Nothing is shared between tenants. The SQL is the same code Bounda runs on SQLite anywhere else.
- **A command updates the read models before it answers.** The object stores the events and
  projects them in the same request, so the query that follows sees the change: that is why the
  API test can pay and then list without waiting.
- **Policies and timers run in the object's alarm.** Right after the command answers, the object
  arms its alarm, and the alarm runs the policy: `expire-on-order-placed` runs there, and stores
  `expireOrder` as a scheduled command. The object then arms its alarm for when that command is
  due, 30 minutes later. A slow policy never slows the command down, and an object with nothing
  pending arms nothing.
- **A policy runs at least once, with an inbox.** Its attempt commits everything it decided in
  one transaction or nothing, and an event it has handled is not handled again. The details are
  in [delivery guarantees](https://docs.bounda.dev/concepts/delivery-guarantees/).

## What it costs

Durable Objects with SQLite bill by the row, so the honest measure of a command is a count of
rows. Each SQLite cursor in a Durable Object reports the rows it read and wrote, index updates
included, which is what Cloudflare bills. Counting them for the template's `placeOrder`, after
the first command has created the schema, gives **8 rows written**:

| Rows | What |
|---|---|
| 4 | The event, with the event store's indexes |
| 3 | The read-model row, with its primary key and its `customerId` index |
| 1 | The read model's checkpoint |

It reads 13. A command sent with an idempotency key writes 3 more, to remember its answer.

With Cloudflare's prices, as published on the
[Durable Objects pricing page](https://developers.cloudflare.com/durable-objects/platform/pricing/)
(last updated 18 October 2026) and the
[Workers pricing page](https://developers.cloudflare.com/workers/platform/pricing/)
(2 October 2026), both checked on 7 November 2026:

- **On the Free plan**, rows written run out first: 100,000 a day is about **12,500 commands a
  day** like this one. Past it, writes fail until the day resets at 00:00 UTC.
- **On the Paid plan** ($5 a month), 50 million rows written a month are included, which is
  **6.25 million commands**. Past that, a million more cost **about $8.50**: $8.00 in rows
  written, $0.15 in Durable Object requests, $0.30 in Worker requests, and cents in rows read and
  duration.

Storage is billed apart, at $0.20 per GB-month past 5 GB-month on Paid, and an event store only
grows.

The app you just built costs more per order, because its policy has work to do in the alarm:
the inbox entry that makes it run once, the scheduled `expireOrder`, a checkpoint, and one row
each time the object arms its alarm. Measured with the same instrumentation, that came to
**roughly twice the template's rows, and a second request, per order placed**, not counting the
expiry itself, which runs half an hour later. Writes are the bill, and every `.index()` in a view
and every policy is a line on it.

The figures come from this test, about 25 lines in workerd. Add it as `tests/cost.test.ts` to the
template and `npm test` checks the 8:

```ts
// tests/cost.test.ts
import { connect } from "@bounda-dev/cloudflare";
import { env, runInDurableObject } from "cloudflare:test";
import { expect, it } from "vitest";

const cursors: SqlStorageCursor<Record<string, SqlStorageValue>>[] = [];

it("counts the rows a command writes", async () => {
  const stub = env.STORE.get(env.STORE.idFromName("cost"));
  const store = connect(stub);
  // The first command creates the schema; measure the ones after it.
  await store.commands.placeOrder({ orderId: crypto.randomUUID(), customerId: "ada", total: 1 });

  await runInDurableObject(stub, (_object, state) => {
    const sql = Object.getPrototypeOf(state.storage.sql);
    const exec = sql.exec;
    sql.exec = function (this: SqlStorage, ...args: Parameters<SqlStorage["exec"]>) {
      const cursor = exec.apply(this, args);
      cursors.push(cursor);
      return cursor;
    };
  });

  await store.commands.placeOrder({ orderId: crypto.randomUUID(), customerId: "ada", total: 42 });
  const written = cursors.reduce((sum, cursor) => sum + cursor.rowsWritten, 0);
  expect(written).toBe(8);
});
```

It counts what happens until the command answers, so it still passes after step 4: the policy's
rows arrive later, in the alarm. Every figure here was measured on 7 November 2026 with Bounda
0.3.0, wrangler 4.158 and `@cloudflare/vitest-plugin` 1.6; a later version can write a different
number of rows, and the test is how to know. In production, the Durable Objects metrics in
Cloudflare's dashboard show the rows each namespace reads and writes.

## When it is the wrong design

One object per tenant is a strong default when tenants are independent and most of them are
quiet at any given moment. It fits badly when one tenant writes without pause: an object is a
single writer that commits one command at a time, with a soft limit of about 1,000 requests a
second, so a shared order book or a global counter queues behind itself. It fits badly when users
are far from the object, because an object lives in one place and a user on another continent
pays the round trip on every command. Each object's SQLite holds 10 GB on the Paid plan, and since
events are never deleted, a tenant that will keep that much history needs it split by something
the domain already knows, such as a year. And each tenant's read models live in its own object,
so a report across every tenant needs the events copied somewhere else, a pipeline that is yours
to build.
