遅かれ早かれ、こんなメールが届きます。*私について保有しているデータをすべて削除してください*。状態をテーブルに保存するシステムなら、`DELETE` 文を書いてバックアップを確認する午後の作業で済みます。イベントソーシングのシステムなら、存在意義が揺らぎます。イベントストアの要点は、そこに入ったものは決して変更も削除もされないことです。だからこそ再構築は正確で、監査証跡は完全で、バグは再現できます。ところが法律、つまり GDPR 第17条は、ある一人の人に関する部分は消さなければならないと言います。

チームが取りがちな答えは二つあり、どちらも間違っています。一つ目は履歴を書き換えること。その人のイベントを探して、その場で編集します。これはログが約束していたことをすべて破り、バックアップにも、コンシューマーがすでに持っていったコピーにも届かず、追記のみのストアを「ときどき追記のみではない」ストアに変えてしまいます。二つ目は、ログは特別だから法律は適用されないと決めてしまうこと。適用されます。

三つ目の答えがあります。そしてそれは、多くのチームが飛ばしてしまう問いから始まります。

## そのフィールドは、そもそもイベントに入れるべきか?

イベントは決定を記録するものです。`OrderPlaced` は、顧客 `c-42` が商品を二つ注文したという事実です。その人の名前、住所、電話番号はこの事実の一部ではありません。配送業者が必要とし、請求書に印字される詳細情報です。「コマンドに入っていたから」とそれらをイベントにコピーするコマンドハンドラーは、システムの別の部分が持つべきデータの所有者をイベントにしてしまっています。

ですから、最初の道具は暗号ではなく境界です。イベントは ID だけを持ち、詳細は削除できる実装を持つポートの向こう側に置きます。その人を消すことは、そのストアに対する `DELETE` です。Mathias Verraes はこれを [forgettable payloads](https://verraes.net/2019/05/eventsourcing-patterns-forgettable-payloads) と呼んでいます。過去を説明するのにそのデータが要らない限りはこれで十分で、しかもデータをログのすべてのコピーから遠ざけられます。

けれども、ときにはデータこそが決定*そのもの*です。`AddressChanged` は引っ越し先の住所を記録します。`EmailVerified` はどのメールアドレスが検証されたかを記録します。`ComplaintFiled` は顧客が書いた内容を記録します。データを取り除けば、イベントは意味を失います。こうしたフィールドはログに残り、それを忘れる仕組みはログそのものの上で、すべてのバックアップに対して、1 バイトも書き換えずに機能しなければなりません。

## 鍵を捨てる

それがクリプトシュレッディングです。一人ひとりに鍵があり、その人のフィールドはその鍵で暗号化して保存されます。その人を忘れるとは、鍵を削除することです。イベントはまったく同じ場所に残り、中身はそれ以降ただのノイズになります。稼働中のデータベースでも、それ以前に取られたすべてのコピーでも。

ある顧客のストリームの前後を見てみましょう。

| ポジション | イベント | 忘れる前のメール | 忘れた後のメール |
|---|---|---|---|
| `000 118` | `CustomerRegistered` | `ana@example.com` | `null` |
| `000 342` | `EmailChanged` | `ana@work.example` | `null` |
| `000 977` | `OrderPlaced` | (個人フィールドなし) | (個人フィールドなし) |
| `001 204` | `PersonalDataForgotten` | | |

最後の行より上は何も編集されていません。ポジションも、イベントの型も同じです。注文は今までどおり畳み込まれ、リードモデルも今までどおり再構築されます。消えたのは鍵だけです。

[Bounda](https://docs.bounda.dev/getting-started/) では、フィールドに印を付けるのはイベントのスキーマに一語足すだけです。

```ts
// app/domain/customer/customer-registered.ts
export const payload = ({ z, personal }: Event.PayloadArgs) =>
  z.object({ email: personal(z.email()), plan: z.enum(["free", "pro"]) });
```

そして誰かを忘れるのは、呼び出し一回です。

```ts
await app.forget("c-42");
```

## 肝心なのは `null`

私がいちばん大事にしている細部は型です。イベントを*書く*側は `string` を渡します。それを*読む*側、つまり畳み込み、プロジェクション、ポリシーは `string | null` を受け取ります。

この `null` は好みの問題ではありません。メールアドレスが必ずあると思い込んでいたすべての場所へ、コンパイラーが連れて行ってくれるのです。`NOT NULL` の列にコピーしていたプロジェクション、小文字に変換していた畳み込み、ウェルカムメールを送るポリシー。忘れられた人のイベントも、畳み込まれ、投影され、再生され続けます。データがあった場所に穴が空いているだけです。そしてあなたのコードは、最初の削除依頼が届く前に、その穴が何を意味するかを決めておくことを強いられます。後からではありません。

何年も前からクリプトシュレッディングを提供している Axon は、忘れられた `String` をデフォルトで `""` として返します。データは消えていても、型は何も起きていないと言い、それを読むコードは決して気づきません。

## 難しいのはコピーのほう

鍵を削除すればイベントは読めなくなります。しかし、イベントから作られたものには何もしません。そしてイベントソーシングのシステムでは、イベントから多くのものが作られます。

- **リードモデル。** 顧客ディレクトリはメールアドレスを行に投影しました。
- **スナップショット。** 集約の畳み込まれた状態。長いストリームを速く読み込むため、平文でキャッシュされています。
- **記憶された応答。** 冪等性キー付きで送られたコマンドは自分の応答を保存し、拒否のメッセージには判断の元になった状態が引用されているかもしれません。
- **予約された処理。** 来週のリマインダーがキューに入っていて、ペイロードにメールアドレスがあります。
- **デッドレター。** あきらめたコマンドが、ペイロードごと運用者のために残されています。
- **外の世界。** ウェルカムメールを送ったとき、メール配信サービスは連絡先を受け取りました。

多くの実装が「忘れた」の意味について誠実でなくなるのは、ここです。Bounda では、`forget` が鍵を削除するのと同じトランザクションの中で、ランタイム自身のコピーを処理します。その人のフィールドを含むスナップショットと記憶された応答を削除し、それを運ぶ予約済みコマンドを取り消し、そのデッドレターを削除します。そのうえで、その人自身のストリームに `PersonalDataForgotten` というイベントをもう一つ追加します。

このイベントこそ、アプリの残りの部分が必要とするものです。個人フィールドを投影するリードモデルは「忘れる」ことも投影しなければならず、そうするまでは Bounda が生成する型がコンパイルに失敗し、どのリードモデルにどのファイルを足せばよいかを教えてくれます。

```ts
// app/read/customer-directory/projections/bounda/personal-data-forgotten.ts
export const project = async ({ event, table }: Projection.Args) => {
  await table.delete({ customerId: event.payload.personId });
};
```

そして同じイベントに対するポリシーが、外の世界に知らせる場所です。メール配信サービスの連絡先を消し、検索インデックスからプロフィールを外します。

## ほかはどうしているか

| | 忘れ方 | 破壊的か | アプリに何が知らせるか |
|---|---|---|---|
| **Marten** | イベント型ごとのマスキング規則が保存済みの行を書き換える | はい | なし。プロジェクションには再構築後に反映 |
| **Axon** | クリプトシュレッディング(商用モジュール) | いいえ | なし。忘れられた文字列は `""` として読まれる |
| **KurrentDB** | ストリーム全体を削除または期限切れにし、後で scavenge がディスクから消す | はい(ストリーム単位) | なし |
| **Bounda** | クリプトシュレッディング(標準機能) | いいえ | `PersonalDataForgotten` イベントと、型の中の `null` |

Marten のドキュメント自体が、クリプトシュレッディングはまだ検討中だと書いています。KurrentDB はフィールド単位の消去をアプリケーションに任せています。Bounda にいちばん近いのは Axon のやり方ですが、違いが三つあります。Bounda の鍵はイベントと同じデータベースにあるので、バックアップと復元で両者が一緒に保たれ、テストに二つ目のストアは要りません。忘れられた値はデータでも型でも `null` です。そして「忘れる」こと自体がイベントです。それが起きたとき、リードモデルとポリシーにはやるべき仕事があるからです。

## 解決しないこと

フレームワークが提供できるのは仕組みです。あなたを法令遵守にすることはできません。できると言う人は、何かを売り込んでいます。

- **バックアップは鍵を保持します。** 鍵はイベントの隣にあるので、データベースのバックアップは、保管されている限りデータのコピーです。
- **ログは出力したものを保持します。** ハンドラーがペイロードをログに書けば、そこに平文で残ります。
- **システムの外に出たものは外に残ります。** ポリシーが消しに行かない限り。
- **印のないフィールドは平文です。** 印はイベントごと、フィールドごとです。付け忘れれば、永遠に読めてしまいます。
- **鍵のない暗号文がなお個人データにあたるかどうか**は法律の問題です。Verraes はこの問いを提起していますが、ここで答えるつもりはありません。

アクセス、ポータビリティ、保存期間、処理の制限といった、フレームワークが担える残りの権利は、Bounda の次のマイナーリリースのテーマです。

## 実際に見てみる

[ライブデモ](https://demo.bounda.dev)は、訪問者ごとに一つの Durable Object で Bounda を動かしている劇場のチケット窓口です。席を買ってから、**Forget me** というシーンを開いてください。あなたのメールアドレスは、どれほど古いイベントからも、売上台帳からも消えます。予約はリードモデルから外れ、あなた宛てに予約されていたリマインダーは取り消されます。ストリームはすべてのポジションを保ったままです。

残りは[個人データのガイド](https://docs.bounda.dev/guides/personal-data/)(英語)にあります。ポートで十分な場合とそうでない場合については、[Forgetting in an immutable log](https://docs.bounda.dev/concepts/forgetting-in-an-immutable-log/)(英語)が詳しく扱っています。
