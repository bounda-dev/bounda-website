イベントストアは、動くマシンに三つのことを求めます。一つのストアのイベントが一つの順序を持つための、単一の書き手。複数の行をまとめてコミットできる永続ストレージ。そして、コマンドの後に続く処理(ポリシー、リマインダー、リトライ)のために、あとで目を覚ます仕組みです。

Cloudflare の Durable Object はまさにそれです。自前の SQLite データベースとアラームを持つ、シングルスレッドのアクターです。だから [Bounda](https://docs.bounda.dev/getting-started/) は、イベントソーシングのアプリをまるごと一つに収められます。テナントごとに一つのオブジェクトが、イベントストア、リードモデル、ポリシーとプロセスの受信箱、予約されたコマンド、デッドレターを持ちます。動かし続けるキューも、cron も、二つ目のデータベースもありません。

この記事は、その費用についてです。Durable Object はストレージを行単位で課金するので、正直な答えは行数の勘定になります。そしてその勘定は、丸ごと見せられるほど小さいものです。

## 一つのコマンドを順に

コマンドは Worker を経由して、RPC でオブジェクトに届きます。オブジェクトは集約のイベントを読み込み、状態に畳み込み、ハンドラーを実行し、返されたイベントを保存します。応答する前に、それらのイベントを投影するすべてのリードモデルを同じオブジェクトの中で最新にするので、続くクエリはもう変更を見られます。

イベントに反応するもの、つまりポリシーやプロセスは、コマンドが応答した直後にオブジェクトのアラームで動きます。オブジェクトは処理が残っていれば自分でアラームをセットし、なければセットしません。何も受け取らないテナントにかかるのは、保存しているバイトの分だけです。

## 8 行

`npm create bounda@0.3.0` が書き出す Cloudflare プロジェクトを、アプリには一行も手を加えずに生成し、オブジェクトが実行したすべての文を数えました。Durable Object の SQLite カーソルはそれぞれ `rowsWritten` と `rowsRead` を報告し、Cloudflare が課金するのはその数字で、インデックスの更新も含まれます。アプリには集約 `order` とそのコマンド `placeOrder`、そしてリードモデル `orders` が一つあり、そのビューには主キーと `customerId` のインデックスがあります。

最初のコマンドがスキーマを作った後の `placeOrder` 一回は、**8 行**を書きます。

| 行 | 内容 |
|---|---|
| 4 | イベントと、イベントストアのインデックス |
| 3 | リードモデルの行と、その主キーと `customerId` のインデックス |
| 1 | リードモデルのチェックポイント |

読むのは 13 行です。注文を一件見つける `listOrders` クエリは 3 行を読みます。ハンドラーが拒否したコマンド(`AlreadyPlaced`)は何も書きません。拒否は事実ではないので、何も保存されないのです。

真ん中の行は、あなたが決められるものです。ビューの `.index()` は一つごとに、そのビューの行が変わるたびに書き込む行を一つ増やします。Durable Object では、インデックスは性能の判断であると同時に、請求額の判断でもあります。

よく使う他の操作も、同じ方法で測りました。

| 操作 | 書き込み行 | 読み取り行 | リクエスト |
|---|---|---|---|
| `placeOrder` | 8 | 13 | 1 |
| `placeOrder`(拒否) | 0 | 2 | 1 |
| `listOrders`(1 行) | 0 | 3 | 1 |
| 冪等性キー付きの `placeOrder` | 11 | 15 | 1 |
| 同じキーでもう一度 | 0 | 6 | 1 |
| 冪等性キー付きの拒否 | 3 | 4 | 1 |
| `consistency: "eventual"` の `placeOrder` | 9 | 約 29 | 2 |
| `placeOrder` とコマンドを送るポリシー | 19 | 約 67 | 2 |
| 保留中の処理がないアラーム | セットされない | | 0 |

書き込み行には、オブジェクトがアラームをセットするたびの 1 行が含まれます。Cloudflare はこれを 1 行の書き込みとして課金します。実行されたアラームは、さらに 1 リクエストです。

このうち三つは、もう少し詳しく見る価値があります。

**ここでは結果整合性は何も節約しません。** リードモデルが最新になる前に応答するコマンドも、同じ 8 行にアラームを加えて書き、それを投影するアラームが二つ目のリクエストになります。得られるのはより早く応答するコマンドであって、より安いコマンドではありません。

**ポリシーは請求を倍にしますが、それは妥当です。** このポリシーは、注文が入るたびに `confirmOrder` を送って確定させます。つまり、自前のイベントを持つ二つ目のコマンド、ポリシーの試行を全部か無かでコミットする受信箱の行、そしてストリームを追うチェックポイントです。二つのコマンドと、途中で止まることのない一つの反応で 19 行です。

**冪等性キーは 3 行かかり、残りを節約します。** キーは応答と一緒に、イベントと同じトランザクションで保存されます。同じキーでのリトライは何も書かず、最初の試行と同じ応答を返します。キー付きの拒否も記憶されるので、普通の拒否が何も書かないところで 3 行を書きます。

## 8 行のコスト

価格と制限は、Cloudflare の [Durable Objects の料金](https://developers.cloudflare.com/durable-objects/platform/pricing/)(2026 年 10 月 18 日更新)、[制限](https://developers.cloudflare.com/durable-objects/platform/limits/)(2026 年 11 月 7 日)、[Workers の料金](https://developers.cloudflare.com/workers/platform/pricing/)(2026 年 10 月 2 日)のページ(英語)によります。

**Free プラン**では、先に尽きるのは書き込み行です。1 日 100,000 行は、このようなコマンドで **1 日約 12,500 件**です。リクエスト(1 日 100,000)と読み取り行(1 日 500 万)には遠く及びません。どの上限を超えても、その種類の操作は 00:00 UTC に日が切り替わるまで失敗します。

**Paid プラン**(月 5 ドル)には、月 5,000 万行の書き込みが含まれます。これは **625 万コマンド**です。Durable Object のリクエストは月 100 万で先に尽きますが安価で、残りの 525 万は 1 ドル未満です。含まれる分を超えると、100 万コマンドごとの費用は次のとおりです。

| | 100 万コマンドあたり |
|---|---|
| 書き込み 800 万行(100 万行あたり 1.00 ドル) | 8.00 ドル |
| Durable Object へのリクエスト 100 万 | 0.15 ドル |
| 前段の Worker へのリクエスト 100 万 | 0.30 ドル |
| 読み取り 1,300 万行 | 約 0.01 ドル |
| 実行時間 | 0.02 ドル未満 |
| **合計** | **約 8.50 ドル** |

実行時間は、オブジェクトがアクティブな間の実時間で、128 MB として課金されます。ノートパソコン上のローカルの workerd では、一つのコマンドは約 0.5 ミリ秒でした。本番ではもっと遅くなりますが、10 ミリ秒としても 100 万コマンドで 1,250 GB-s で、含まれる 400,000 GB-s に比べればわずかです。アイドルで休止できるオブジェクトには実行時間の課金がなく、保留中の処理がないオブジェクトには起こすアラームもありません。

**ストレージ**は、このアプリでコマンドあたり約 600 バイト(イベントとリードモデルの行の合計)増えました。100 万コマンドで約 0.6 GB で、しかも積み上がります。イベントは削除されないので、バイトは残り続けます。5 GB-月が含まれ、その後は 1 GB-月あたり 0.20 ドルです。

傾向ははっきりしています。請求額を決めるのは書き込みです。自分の量に掛けるべきなのは上の行数で、ビューのインデックスが変えるのもその行数です。

## 0.3.0 で変わったこと

冪等性キーとスナップショットは、どちらも Bounda 0.3.0 で入りました。前者はすでに上にあります。安全にリトライできるコマンドのための 3 行です。

面白いのはスナップショットです。Durable Object の上では、期待どおりのことをしないからです。同じアプリに `addLine` コマンドを足し、一つの注文に 400 回送りました。最初はスナップショットなしで、次に 100 イベントごとのスナップショットありで。

| 400 イベントのストリーム | コマンドあたりの書き込み行 | コマンドあたりの読み取り行 |
|---|---|---|
| スナップショットなし | 6 | 429(イベントごとに 1 ずつ増える) |
| 100 イベントごとのスナップショット | 7 | 約 44 と、最後のスナップショット以降の最大 100 |

スナップショットがなければ、コマンドはストリーム全体を読むので、読み取りはイベントごとに増えます。あれば、スナップショットとその後のイベントだけを読みます。増えた 1 行は、リードモデルと同じようにグローバルストリームを追うスナップショット購読者のチェックポイントです。スナップショットそのものは 100 イベントごとに 1 行を加えます。400 コマンドで、スナップショットは約 53,000 行の読み取りを減らし、約 400 行の書き込みを増やしました。

Cloudflare の価格では、53,000 行の読み取りは 0.005 セント、400 行の書き込みは 0.04 セントです。**Durable Object の上では、スナップショットは請求額ではなくレイテンシーのための判断です。** 429 行ではなく 44 行を畳み込むコマンドが手に入り、少しだけ高くつきます。たいていの集約にとってより良い手は、ストリームを短くすることです。期間を締めて、次の期間を開きます([long streams](https://docs.bounda.dev/concepts/long-streams/)、英語)。

`addLine` の行はもう一つのことを示しています。そのイベントを投影するリードモデルはないので、コマンドはどれにも触れずに応答し、続くアラームがリードモデルのチェックポイントをその先に進めます。それが 6 行目であり、二つ目のリクエストです。

## 約束すること、しないこと

- **リードモデルはバッチごとに正確に一度だけ更新されます。** 行とチェックポイントは一つのトランザクションでコミットされるので、途中で落ちてもどちらも残りません。
- **ポリシーとプロセスは、受信箱を使って少なくとも一度は実行されます。** 一回の試行は、決めたことをすべて一つのトランザクションで書くか、何も書かないかで、外部へは `idempotencyKey` を付けて呼び出します。
- **一つのオブジェクトは一つの書き手です。** スケールはテナントを増やすことで行い、一つのテナントのストリームを分割することでは行いません。

詳しくは [delivery guarantees](https://docs.bounda.dev/concepts/delivery-guarantees/)、[how it runs](https://docs.bounda.dev/concepts/how-it-runs/)、[Cloudflare アダプター](https://docs.bounda.dev/adapters/cloudflare/)(いずれも英語)にあります。

## この設計が向かないとき

テナントごとに一つのオブジェクトという形は、テナントが互いに独立した SaaS には強い既定値です。仕事がそのように分かれないときには、よく合いません。

- **一つのテナントが書き込みすぎる。** オブジェクトは一つのスレッドで動き、コマンドを一つずつコミットします。Cloudflare はオブジェクトあたりの目安の上限を毎秒約 1,000 リクエストとしています。共有された一つの板、グローバルなカウンター、他を圧倒する一つの大きなテナント。そのコマンドはすべて順番待ちになります。
- **ユーザーがオブジェクトから遠い。** オブジェクトは一つのリージョンに住み、別の大陸のユーザーはコマンドのたびに往復の遅延を払います。
- **一つのテナントが大量の履歴を持つ。** オブジェクトの SQLite は 10 GB までです。コマンドあたり 600 バイトなら、イベントストアは増えるだけなので、生涯で約 1,600 万コマンドです。それを超えそうなテナントは、年や地域のように、ドメインがすでに知っている何かで履歴を分ける必要があります。
- **テナントをまたいで問い合わせる。** 各オブジェクトは自分のリードモデルを持ちます。全テナントにわたるレポートには、イベントを別の場所にコピーする必要があり、そのパイプラインは自分で作ることになります。
- **量が一定で多い。** 100 万あたり 8.50 ドルだと、毎日数百万のコマンドは積み上がり、月額で借りるマシン上のデータベースのほうが安くなることがあります。Durable Object が勝つのは、負荷が多くのテナントに散らばり、その多くがアイドルなときです。

必要なのがオブジェクトの履歴ではなく現在の状態なら、[Agents SDK](https://developers.cloudflare.com/agents/) の `setState()` のほうが少ない仕組みでそれを保てます。イベントソーシングがその行数に見合うのは、問いが過去についてのときです。なぜ注文がキャンセルされたのか、先月ダッシュボードに何が表示されていたのか、新しい機能がすでにあるデータから何を学べるのか。

## 自分で数える

上の数字は、Cloudflare の Vitest 連携を使った workerd 上のテストから得たものです。生成されたプロジェクトは、もともとこの方法でテストを実行します。プロジェクトを作り、ファイルを一つ足してください。

```bash
npm create bounda@0.3.0 cost -- --runtime cloudflare
```

```ts
// tests/cost.test.ts
import { connect } from "@bounda-dev/cloudflare";
import { env, runInDurableObject } from "cloudflare:test";
import { expect, it } from "vitest";

const cursors: SqlStorageCursor<Record<string, SqlStorageValue>>[] = [];

it("counts the rows a command writes", async () => {
  const stub = env.STORE.get(env.STORE.idFromName("cost"));
  const store = connect(stub);
  // The first command creates the schema; measure the ones after it.
  await store.commands.placeOrder({ orderId: crypto.randomUUID(), customerId: "ada", total: 1 });

  await runInDurableObject(stub, (_object, state) => {
    const sql = Object.getPrototypeOf(state.storage.sql);
    const exec = sql.exec;
    sql.exec = function (this: SqlStorage, ...args: Parameters<SqlStorage["exec"]>) {
      const cursor = exec.apply(this, args);
      cursors.push(cursor);
      return cursor;
    };
  });

  await store.commands.placeOrder({ orderId: crypto.randomUUID(), customerId: "ada", total: 42 });
  const written = cursors.reduce((sum, cursor) => sum + cursor.rowsWritten, 0);
  expect(written).toBe(8);
});
```

`npm test` で実行できます。オブジェクトが実行するすべての文は `exec` を通り、各カーソルは自分の行数を数えます。コマンドを変え、ポリシーやインデックスを足せば、数はそれに従います。本番では、Cloudflare のダッシュボードにある Durable Objects のメトリクスが、名前空間ごとの読み取り行と書き込み行を示します。

ここの数字はすべて、2026 年 11 月 7 日に Bounda 0.3.0、wrangler 4.158、`@cloudflare/vitest-plugin` 1.6 で測ったものです。後のバージョンでは書く行数が変わるかもしれません。それを知る方法がこのテストです。

## 試してみる

[ライブデモ](https://demo.bounda.dev)は、訪問者ごとに一つの Durable Object を持つ劇場のチケット窓口です。**Rush hour** というシーンを開いてください。六人の購入者が一度にやってきて、席を押さえると、あなたのコマンドが公演のどれだけをスナップショットから畳み込んだかが表示されます。自分の環境にデプロイするなら、[Deploy to Cloudflare](https://deploy.workers.cloudflare.com/?url=https://github.com/bounda-dev/bounda-cloudflare-template) ボタンか `npm create bounda@latest my-app -- --runtime cloudflare` を使ってください。
